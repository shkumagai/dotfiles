# 委任先のセッション（別の Claude Code）に任せる

## 0. 最初に config.yaml と backend のファイルを読む

この skill と同じディレクトリの `config.yaml` に、このユーザーの値（使う TUI ツール、自分の作業場所の表示名、固定のセッション、環境の決まり、定型の作業など）がある。以下で `self_display_name` や `fixed_agents.tracker` のように書いたものは、config.yaml のキーを指す。

- 最初に `config.yaml` を読む。
- 無ければ、作業を始める前に、同じディレクトリの `config.example.yaml` をもとに、ユーザーと対話しながら `config.yaml` を作る。
  - example のキーを順に示し、値を 1 つずつ聞く（AskUserQuestion など）。分かる値（読み取りで確かめられるもの）は、候補として示して確かめてもらう。推測で埋めない。
  - できあがった内容を見せ、ユーザーの了承を得てから保存する。保存したら、元の作業に戻る。
- 次に、config の `backend` に対応する `backends/<backend>.md` を読む。下の「操作」を、そのツールでどう行うか（コマンド、はまりやすい点）が書いてある。
- `backends/<backend>.md` が無ければ、作業を始める前に、`backends/TEMPLATE.md` をもとに、ユーザーと対話しながら作る。
  - TEMPLATE.md の操作を順に埋める。ツールの `--help` や公式のドキュメントを読み取りで確かめ、分かったコマンドを候補として示して確かめてもらう。
  - 確かめられないコマンドは推測で書かず、ユーザーに聞くか「未確認」と書く。
  - できあがった内容を見せ、ユーザーの了承を得てから保存する。保存したら、元の作業に戻る。

### 用語と操作

この skill では、ツールに依らない次の言葉を使う。ツールでの呼び名は backend のファイルにある。

- **作業場所**: 委任先のセッション 1 つ分の、端末の中の場所。ユーザーが一覧で見分けられ、あとから個別に開ける。
- **表示名**: 作業場所に付ける、ユーザーに見える名前。
- **エージェント名**: 操作で委任先のセッションを名指しするときの名前。
- **起動先**: 作業場所を作ったときに返る、エージェントを起動する場所の識別子。
- **状態**: 委任先のセッションが「作業中」「終わった・入力待ち」「確認待ち（許可の確認などで止まっている）」のどれか。

Claude Code の公式の用語とは、次のように対応する。
- 委任先のセッションは、公式の用語では、それぞれ独立したセッションにあたる。会話の履歴も transcript も別になる。
- 公式の「サブエージェント」は、Agent ツールで 1 つのセッションの中に作る、別の文脈のこと。この skill では「サブエージェント（Agent ツール）」と書く。
- サブエージェント（Agent ツール）は使わない。理由は「進め方の基本」にある。
- 根拠: https://code.claude.com/docs/en/sub-agents 、https://code.claude.com/docs/en/sessions

操作は次のとおり。手順の中では、この名前で書く。

| 操作 | 入力 | 出力 |
|---|---|---|
| 作業場所の一覧を見る | なし | 作業場所ごとの識別子と表示名 |
| 作業場所の表示名を付け直す | 作業場所の識別子、新しい表示名 | なし |
| 作業場所を作る | 作業ディレクトリ、表示名 | 作業場所の識別子、起動先 |
| エージェントを起動する | エージェント名、起動先、claude に渡す引数（任意） | 入力を受け付けられるようになったか |
| エージェントの一覧を見る | なし | 生きているエージェントの名前と状態 |
| プロンプトを送る | エージェント名、文 | 送信できたか |
| 出力を読む | エージェント名、行数（任意） | 画面の最近の内容 |
| 状態を待つ | 報告ファイルのパス、エージェント名 | 状態（またはタイムアウト） |
| 作業場所を閉じる | 作業場所の識別子 | なし |
| git の worktree を用意する（任意） | リポジトリ、ブランチ | worktree のパス |

## 進め方の基本

依頼された作業は、基本的にすべて委任先のセッションに指示し、バックグラウンドで待つ。自分は、指示書を書く、進み具合を見る、結果を確かめてユーザーに報告する、という役に徹する。待っている間も、ユーザーとの会話は続けられる。

自分で直接やってよいのは、次のものだけ。
- 質問への回答や相談。会話の中で答えられるもの
- 指示書を書くための、ちょっとした事前確認（数回のコマンドで済む読み取り）
- 委任先のセッションの結果の確かめ（読み取りだけ）
- 作業場所やエージェント自体の操作（上の「操作」）

委任先のセッションは、作業場所ごとに別の Claude Code として起動する。サブエージェント（Agent ツール）は使わない。
- 理由: ユーザーが TUI ツール上で、何が動いているかを一目で見られるようにするため。あとから個別に再開もできる。
- 操作で迷ったら、backend のファイルの「困ったときの参照」を見る。

## 1. 指示書を書く

スクラッチパッドに `<task>-brief.md` を置く。委任先のセッションは、この会話の文脈を知らない。だから、次の 5 つを必ず書く。
- **背景**: なぜやるのか、ユーザーと合意したこと
- **対象**: リポジトリ、PR 番号、page id、cloudId、URL など
- **やること**: 手順と判断の基準。結論を先に出させたいならそう書く
- **守ること**: 下の「共通の制約」と、config の `constraints` を貼る。書き込んでよい先を 1 つずつ明示する
  - 対象のリポジトリに CLAUDE.md があれば、委任する前に禁止事項を確かめ、指示書に写す
  - `~/.claude/CLAUDE.md` の「どのセッションでも守ること」は、委任先のセッションも読む。指示書に重ねて書かない
- **報告**: スクラッチパッドの `<task>.md` に、何を書くか

## 2. 起動する

### 固定のセッション

config の `fixed_agents` に書いた役割の作業は、決まったセッションにだけ任せる。タスクごとに新しく作らない。

| 役割 | 作業 | エージェント名 | 作業場所の表示名 | 作業ディレクトリ |
|---|---|---|---|---|
| `tracker` | 課題管理への同期（ステータス遷移、説明・担当・コメントの更新など、課題管理への書き込みすべて） | `fixed_agents.tracker.name` | `fixed_agents.tracker.display_name` | `default_cwd` |
| `wiki` | wiki への記録（ページの作成と更新すべて） | `fixed_agents.wiki.name` | `fixed_agents.wiki.display_name` | `default_cwd` |

- どのサービスに書くかは、依頼で指定が無ければ、config の `fixed_agents.<役割>.default_service` に従う。サービスごとの具体的な手順は、`fixed_agents.<役割>.services` でそのサービスに対応づけた skill にある。
- 指示書には、使うサービスと skill を書く。skill の名前は、config の `fixed_agents.<役割>.services` で確かめる（例: 「`<skill 名>` skill に従って書く」）。
- 指定されたサービスが `services` に無い（skill が無い）ときは、ユーザーに伝える。手順を指示書に詳しく書いて進めるか、先に skill を作るかを決めてもらう。
- 何を書くかの判断（課題管理とのズレの調査など）は自分で行う。指示書には、対象ごとの変更前と変更後、コメントの文面まで書く。

- セッションを起動した直後に、「作業場所の一覧を見る」で自分の作業場所の表示名を確かめる。
  - 固定のセッションの表示名（`fixed_agents.*.display_name`。以前の名前の `legacy_display_names` も含む）が自分の作業場所に付いていたら、「作業場所の表示名を付け直す」で `self_display_name` に付け直す。
  - 理由: 端末を再起動したあと、ツールが前の作業場所を表示名ごと残すことがある。その中でメインのセッションが起動すると、固定のセッションと見分けがつかなくなる。
- まず「エージェントの一覧を見る」でエージェントが生きているかを確かめる。生きていれば、そのエージェントに「プロンプトを送る」で新しい指示書を渡す。
- 生きていなければ、上の表の名前と表示名、作業ディレクトリで、下の「タスクごとのセッション」と同じ手順で作り直す。
  - 固定のセッションは、エージェント定義（`~/.claude/agents/<definition>.md`）で起動する。「エージェントを起動する」で、claude に `--agent <fixed_agents.<役割>.definition>` を渡す方法を優先する。
  - `--agent` で起動すると、Claude Code の既定のシステムプロンプトが定義の本文に置き換わる。困ることがあれば、ユーザーに相談したうえで、claude に渡す引数を `--append-system-prompt-file ~/.claude/agents/<definition>.md` に切り替える。
  - 使う skill を config から引いて読む手順は、定義の中に書いてある。
  - 指示書には、報告先のパスを必ず書く。prompt に直接書くときも同じ。
- 前の作業の文脈が残っていて邪魔なときは、指示書の冒頭に「前の作業とは別の依頼」と書く。必要なら「プロンプトを送る」で `/clear` を送ってから指示書を渡す。
- 調査とまとめは、別の委任先のセッションに任せてよい。外部への書き込みだけは、固定のエージェントを通す。
  - 例: wiki に載せる試算は、調査用のエージェントに作らせる。ページへの書き出しは `fixed_agents.wiki` に任せる。

### タスクごとのセッション

`fixed_agents` 以外の作業は、タスクごとにエージェントを作る。エージェント名と表示名には、どちらも `<task>` を使う。

1. 「作業場所を作る」: 作業ディレクトリと表示名 `<task>` を渡し、起動先を受け取る。
2. 「エージェントを起動する」: エージェント名 `<task>` で、起動先に Claude Code を起動する。準備ができるまで待つ。
3. 「プロンプトを送る」: 次の文を送る。
   ```
   指示書 <brief の絶対パス> を読んで、そのとおりに作業してください。終わったら報告を <report の絶対パス> に書いてください。
   ```

注意点:
- 起動が終わる前に送ると、送信されないことがある。送ったあとは「出力を読む」で送信されたかを確かめる。ツールごとの症状と直し方は、backend のファイルにある。
- git の worktree が必要な作業なら、「git の worktree を用意する」を使うか、指示書に worktree のパスとブランチ名を書く。

## 3. 終わるのを待つ

結果は自動では返ってこない。「状態を待つ」で、報告ファイルができ、エージェントが落ち着くのを、バックグラウンドで待つ（Bash の `run_in_background`）。具体的なコマンドとタイムアウトは、backend のファイルにある。

- タイムアウトしたら、もう一度待てばよい。
- 状態が「確認待ち」のときは、許可の確認で止まっている。「出力を読む」で中身を見て、ユーザーに伝える。
- 待っている間、ユーザーに「終わりましたか？」と聞かれたら、推測で答えない。「エージェントの一覧を見る」と報告ファイルの有無を見てから答える。

## 4. 回収して報告する

- 報告ファイルを読む。外部に書き込んだ結果は、自分でも読み取りで確かめてからユーザーに伝える。
  - 確かめ方は、サービスごとの skill の「書いたあとの確認」に従う。GitHub の PR は、config の `constraints` で指定した PR を作る skill の「作ったあとの確認」に従う（指定が無ければ `gh pr view` など）。
- ユーザーへの報告では、報告ファイルの絶対パスも示す。
- ユーザーの確認待ち中に、別の委任先のセッションの報告はしない（確認内容が流れてしまうことを防ぐため）。
  - 複数の委任先のセッションの報告がほぼ同時に発生する場合は、報告内容を出力する前にどの報告から確認するかをユーザーに確認する。
- 作業場所は、ユーザーが閉じてよいと言ってから閉じる（「作業場所を閉じる」）。固定のセッション（`fixed_agents`）は閉じずに残す。

## 共通の制約（指示書の「守ること」に入れる）

どの環境でも入れるもの。config の `constraints` も、あわせて貼る。
書き込み先の制限、外部に出る文面、terraform の決まりは `~/.claude/CLAUDE.md` にあり、委任先のセッションも読むので、ここには書かない。

- マージされていないブランチは削除しない。

## 定型の作業

config の `routines` に書いた作業は、指示書を書かずに、決まった文を渡すだけでよい。

- `trigger` のように頼まれたら、その routine を使う。
- `fixed: false` なら、タスクごとのエージェント（例: `name_example`）を作る。固定のエージェントにはしない。終わって、ユーザーが確かめたら閉じる。
- `fixed: true` なら、`fixed_agents` の該当する役割のエージェントに渡す。
- 手順は `skill` にある。`prompt` の `{date}` と `{report}` を置き換えて、「プロンプトを送る」で渡す。
